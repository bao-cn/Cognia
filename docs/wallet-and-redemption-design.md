# 用户钱包与兑换码设计方案

> 状态：已实施；接口与当前行为以 [API.md](./API.md) 为准  
> 适用范围：Cognia 订阅与 Token 计费模块  
> 关联设计：[订阅与 Token 额度 API 设计](./subscription-billing-api-design.md)

> 实现说明：当前支持整批作废未兑换码，不提供单码作废接口；兑换限流按用户和来源 IP 计数。

## 1. 目标

本方案在现有订阅与 Token 额度功能上增加：

1. 用户持有统一单位的钱包余额，并可查询余额和钱包流水。
2. 兑换码可以代表一个已发布订阅方案、一个已发布 Token 补充包，或一笔钱包余额。
3. 用户可使用钱包余额购买订阅方案和 Token 补充包。
4. 管理员可以创建、查询、作废兑换码批次，并对用户钱包余额进行有审计记录的调整。

本文记录钱包与兑换码的设计依据；已落地接口、权限和事务行为以 `API.md` 中的计费章节为准。

## 2. 核心概念与边界

### 2.1 钱包余额与 Token 额度分离

- **钱包余额**是货币金额，所有用户使用同一个由后台配置的钱包单位；数据库只存整数余额单位，例如后台配置为人民币分时，余额 `12000` 表示 120 元。它用于购买订阅方案和 Token 补充包。
- **Token 额度**是聊天模型调用额度，仍由现有 `sys_token_lot`、`sys_token_ledger` 管理，用于模型调用预扣与结算。
- 钱包金额不直接抵扣模型 Token 用量；Token 额度也不能直接当作钱包余额支付商品。

### 2.2 第一阶段建议规则

- 全站只使用一个钱包单位，由后台配置币种代码、小数位数和单位名称，例如 `CNY`、2 位小数、`分`。余额按 `主币种金额 × 10^小数位数` 转成整数存储；账户按 `userId` 唯一，不按用户或流水拆分币种。
- 商品使用钱包支付时，商品币种必须与当前钱包配置一致，商品价格按配置精度可无损换算成整数钱包单位；不支持的精度组合应由后台校验拒绝。第一阶段不做汇率转换。
- 兑换码为一次性、不拆分的 bearer code。持有有效兑换码的已登录用户可以兑换；第一阶段不绑定指定用户。
- 订阅方案码、Token 补充包码和余额码均在兑换成功后立即履约，不创建外部支付订单。
- 订阅兑换复用现有订阅开通、续期和排队规则；补充包兑换复用现有 Token 分桶和流水逻辑。
- 钱包支付创建正常计费订单，并在同一个事务内扣钱包、标记订单已支付、履约商品。余额不足时整笔回滚。
- 钱包单位配置应在生成余额或未兑换的余额码后保持不变；若需变更币种或精度，必须迁移余额、流水及未兑换余额码的单位快照，不能直接改配置解释历史数字。
- 第一阶段不支持提现、跨币种转换、优惠券、部分兑换码抵扣或退款工作流。需要退款时，使用受审计的管理员余额调整或后续专门退款功能。

## 3. 兑换码行为

| 兑换码类型 | 创建时绑定内容 | 兑换后效果 |
| --- | --- | --- |
| `SUBSCRIPTION` | 订阅方案及方案权益快照 | 创建订阅实例，按现有规则生效 |
| `TOKEN_PACK` | Token 补充包及额度/有效期快照 | 创建 Token 分桶并追加 Token 流水 |
| `WALLET_CREDIT` | 钱包单位整数金额 | 按当前后台配置增加钱包余额并追加钱包流水 |

规则：

- 兑换码包含足够随机性的不可预测内容，兑换时不区分大小写并去掉格式分隔符。
- 创建码时生成一次性明文结果供管理员下载；数据库只保存兑换码摘要，不提供后续查询明文的接口。
- 码批次可设置生效时间、失效时间和备注；批次或单码可作废。已兑换码不可撤销。
- 兑换码本身是 bearer credential：任何获得码值的人都可能先兑换。管理端必须提示安全保管；邮件、日志和审计信息不记录完整码值。
- 兑换必须由登录用户发起。按 `Idempotency-Key` 防止客户端重试导致重复履约；同一用户重放同一请求返回原兑换结果。
- 同一兑换码只能成功兑换一次。并发兑换时只有一个事务可消费该码，其余请求返回“兑换码已使用”。
- 兑换失败时，码状态、兑换记录和权益变更全部回滚；无效、过期、已兑换和已作废应返回明确但不过度泄露批次信息的错误。

### 3.1 商品权益快照

码批次创建时复制商品快照，而不是只保存商品 ID。快照至少包含：

- `SUBSCRIPTION`：方案名称、方案版本、价格币种、有效期、周期额度、模型权限。
- `TOKEN_PACK`：补充包名称、Token 数、币种、有效期。
- `WALLET_CREDIT`：入账整数金额及发码时的钱包单位配置版本/快照。

商品之后被修改或下架，不改变已发出的码所承诺的权益。作废批次只阻止尚未兑换的码。

## 4. 建议数据模型

实际字段及命名遵循现有 `schema.sql` 与 MyBatis-Plus 风格。

| 表 | 用途 | 关键字段建议 |
| --- | --- | --- |
| `sys_billing_setting` | 全站统一的钱包单位配置 | `wallet_currency`、`wallet_fractional_digits`、`wallet_unit_label` |
| `sys_wallet_account` | 用户钱包余额的锁定与快速读取 | `user_id`、`balance_units`、`update_time`；`user_id` 唯一 |
| `sys_wallet_ledger` | 不可变的钱包金额流水 | `user_id`、`wallet_unit_code`、`event_type`、`delta_units`、`balance_after_units`、`source_type`、`source_id`、`request_id`、`created_at` |
| `sys_billing_redeem_batch` | 兑换码批次及统一权益快照 | `batch_no`、`benefit_type`、`product_snapshot`、`code_count`、`valid_from`、`expire_time`、`status`、`operator_id` |
| `sys_billing_redeem_code` | 单个兑换码的摘要与状态 | `batch_id`、`code_hash`、`status`、`redeemed_by`、`redeemed_at`；`code_hash` 唯一 |
| `sys_billing_redemption` | 兑换履约记录及审计 | `code_id`、`user_id`、`idempotency_key`、`benefit_snapshot`、`result_type`、`result_id`、`create_time`；`code_id` 唯一、`user_id + idempotency_key` 唯一 |

### 4.1 钱包记账约束

- `sys_wallet_ledger` 只追加，不直接更新或删除；更正通过新的反向/调整流水完成。
- 钱包账户是流水汇总的可锁定余额投影；每次变更必须在同一事务中锁定账户行、检查余额、更新账户并插入流水。
- `wallet_currency`、`wallet_fractional_digits` 和 `wallet_unit_label` 通过现有计费设置接口配置；修改精度或币种前必须执行迁移，防止余额数字被重新解释。
- 钱包支付用 `source_type=ORDER`、订单 ID 和稳定请求键关联订单；兑换入账使用兑换记录 ID；管理员调整记录操作人和原因。
- 同一业务来源不可重复入账或扣款，使用数据库唯一约束兜底，不能只依赖前端幂等。
- 不允许余额透支；负向管理员调整和购买扣款均须检查锁定后的可用余额。

### 4.2 兑换码存储约束

- 使用密码学安全随机数生成码值；存储规范化码值的 SHA-256 摘要及唯一索引，不存储明文。
- 批次生成的明文码只在创建响应/导出文件中出现一次。导出文件需由管理员主动下载，服务端不持久化明文文件。
- 单码状态建议为 `ISSUED`、`REDEEMED`、`REVOKED`、`EXPIRED`；过期状态可按查询计算，也可由周期任务更新。
- 码状态必须通过条件更新或行锁完成消费，例如只允许将 `ISSUED` 且处于有效期内的码更新为 `REDEEMED`。

## 5. 用户 API 草案

以下路由均使用当前登录用户身份，不接受请求体中的 `userId`。响应沿用 `ApiResponse<T>`，BIGINT ID 对外使用字符串。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/api/v1/billing/me/wallet` | 查询统一钱包余额及当前单位配置 |
| `GET` | `/api/v1/billing/me/wallet/ledger` | 分页查询自己的钱包流水 |
| `GET` | `/api/v1/billing/me/redemptions` | 分页查询自己的兑换记录 |
| `POST` | `/api/v1/billing/redeem` | 兑换订阅、Token 补充包或钱包余额码 |

兑换请求：

```http
POST /api/v1/billing/redeem
Idempotency-Key: 6f0745ac-...
Content-Type: application/json

{
  "code": "ABCD-EFGH-JKLM-NPQR"
}
```

兑换成功响应包含兑换类型、结果摘要及关联记录 ID；余额码应返回入账整数金额和钱包单位，订阅码返回订阅信息，补充包码返回 Token 分桶摘要。响应不得返回码的摘要或其它用户信息。

钱包查询示例：

```json
{
  "balanceUnits": 12000,
  "walletUnit": {
    "currency": "CNY",
    "label": "分",
    "fractionalDigits": 2
  },
  "formattedBalance": "CNY 120.00"
}
```

建议在现有 `GET /api/v1/billing/me` 中增加钱包余额及单位摘要，避免用户页面重复请求；详细流水继续走独立分页接口。

### 5.1 使用钱包购买

扩展现有 `POST /api/v1/billing/orders`，将 `paymentProvider` 增加 `WALLET`：

```json
{
  "productType": "SUBSCRIPTION",
  "productId": "31001",
  "paymentProvider": "WALLET"
}
```

Token 补充包仍使用 `productType: "TOKEN_PACK"`。金额和商品币种由服务端读取当前已发布商品，并复制到订单快照；客户端不能提交金额、币种或用户 ID。钱包支付前校验商品币种及价格精度与后台配置的钱包单位兼容。

- 设商品币种最小单位精度为 `currencyFractionalDigits`，后台钱包配置精度为 `walletFractionalDigits`，则 `walletUnits = priceMinor / 10^currencyFractionalDigits × 10^walletFractionalDigits`。结果必须是非负整数且不溢出；否则该商品不能使用钱包支付。
- 例如商品价格 `3900` 分表示 CNY 39.00；钱包配置为 `CNY`、2 位小数时扣 `3900` 单位，配置为 `CNY`、0 位小数时扣 `39` 单位。无法整除的价格不得静默四舍五入。

钱包支付成功时直接返回已支付订单，不返回第三方跳转信息。钱包扣款证据保存在钱包流水中，不伪造第三方支付交易。相同 `Idempotency-Key` 重试返回同一订单，不能重复扣款或重复发放权益。

## 6. 管理端 API 草案

建议增加独立权限，避免所有计费管理员都能下载兑换码明文或调整钱包：

- `billing:code-read`：查看批次和兑换汇总，不查看已生成明文码。
- `billing:code-manage`：创建批次、导出创建结果、作废未兑换码。
- `billing:wallet-adjust`：管理员手动调账，必须填写原因并写入审计日志。

| 方法 | 路径 | 权限 | 用途 |
| --- | --- | --- | --- |
| `GET / PUT` | `/api/v1/admin/billing/settings` | `billing:read/update` | 查询或更新全站钱包币种、小数位和单位名称 |
| `POST` | `/api/v1/admin/billing/redeem-code-batches` | `billing:code-manage` | 创建兑换码批次并一次性返回明文码 |
| `GET` | `/api/v1/admin/billing/redeem-code-batches` | `billing:code-read` | 查询批次、状态和已兑换统计 |
| `GET` | `/api/v1/admin/billing/redeem-code-batches/{id}` | `billing:code-read` | 查询批次明细和兑换统计，不返回码明文 |
| `POST` | `/api/v1/admin/billing/redeem-code-batches/{id}/revoke` | `billing:code-manage` | 作废批次所有未兑换码 |
| `POST` | `/api/v1/admin/billing/redeem-codes/{id}/revoke` | `billing:code-manage` | 作废单个未兑换码 |
| `POST` | `/api/v1/admin/billing/users/{userId}/wallet-adjustments` | `billing:wallet-adjust` | 有理由地增加或扣减钱包单位余额 |
| `GET` | `/api/v1/admin/billing/users/{userId}/wallet/ledger` | `billing:usage-read` | 查询用户钱包余额及流水 |

创建批次请求建议包括：权益类型、商品 ID 或钱包单位整数金额、数量、生效时间、失效时间、备注。余额码金额应统一；批次生成时记录钱包单位配置快照。服务端对数量和单码金额设置上限，防止误操作生成超大批次或过量价值。

批次创建响应中的明文码仅用于首次下载；列表、详情、日志和后续查询只展示批次号、数量、状态和兑换统计。管理员钱包调整请求必须携带幂等键，并记录操作者、目标用户、变更前后整数余额、钱包单位、原因和关联流水。

## 7. 事务流程

### 7.1 兑换

1. 从登录上下文读取用户 ID，规范化输入码并计算摘要。
2. 在事务中按摘要锁定兑换码；确认批次有效、码未兑换/作废、时间在有效区间。
3. 插入兑换记录并原子地将兑换码标记为已兑换。
4. 根据权益类型调用现有服务：
   - 订阅：复用订阅购买的共同履约逻辑。
   - Token 补充包：创建额度分桶、Token 流水及通知 outbox。
   - 钱包余额：锁定/创建用户账户，按发码时记录的钱包单位配置增加余额并写钱包流水。
5. 提交兑换记录、码状态和权益变更；事务提交后通过 outbox 发送站务通知。

任何一步失败均回滚，不出现“码已消费但权益未到账”或“已发权益但码还能再次兑换”。重复请求通过兑换幂等键返回原结果。

### 7.2 钱包支付订单

1. 校验商品已发布并读取价格、币种和权益快照；确认商品币种和金额精度与后台配置的钱包单位一致。
2. 以用户及 `Idempotency-Key` 创建/查找订单；重复键但商品或支付方式不同则拒绝。
3. 对用户钱包账户行加锁，检查余额充足。
4. 在同一事务中扣减钱包余额并写 `PURCHASE_DEBIT` 流水。
5. 将订单标记为已支付，记录支付时间及内部钱包支付方式。
6. 调用与外部支付确认共用的订单履约逻辑，创建订阅或 Token 分桶、追加相应 Token 流水和通知 outbox。
7. 事务提交后派发通知。

余额不足时不扣款、不履约；支付或履约任何一步失败时整笔事务回滚。外部支付 Webhook 路径保持原有校验，不得将普通客户端请求伪装成已支付回调。

## 8. 安全、幂等与审计

- 兑换码应具备足够随机熵，兑换接口增加按用户/IP 限流和失败次数保护；错误响应避免帮助攻击者枚举有效码。
- 兑换码创建、导出、作废、兑换、钱包调账和余额支付都写审计记录；日志不记录完整兑换码。
- 兑换码使用唯一摘要索引、兑换表唯一 `code_id` 和事务锁共同防重。
- 钱包账户按用户加锁；钱包流水保存钱包单位快照，并使用业务来源和幂等键唯一索引，避免重复扣款或重复入账。
- 钱包余额变动与钱包流水必须同事务提交；所有查询只能读取当前用户自己的余额和流水。
- 只有具备相应管理权限的管理员可创建/作废兑换码或调账；调账理由必填。
- 兑换码过期后不能兑换；过期任务只更新状态，不删除码批次、兑换记录或钱包流水。

## 9. 前端范围

### 用户侧

- 订阅页/计费页展示按后台配置单位格式化后的统一钱包余额。
- 订阅方案和 Token 补充包购买流程提供“钱包余额”支付选项；余额不足时显示所需金额、当前余额，并可返回其他支付渠道。
- 提供兑换码输入与结果反馈；成功后刷新订阅、Token 额度或钱包余额。
- 提供钱包流水和兑换记录列表，标注订单、兑换码批次等来源，但不展示完整兑换码。

### Console

- 增加兑换码批次管理：选择方案/补充包/余额权益，设置数量和有效期，创建后一次性下载码文件。
- 批次列表展示总数、已兑换数、未使用数、过期数、作废数，不再次显示码值。
- 增加用户钱包查询和有理由的加/扣款操作；负向调整不能导致余额小于零。
- 通过细粒度权限控制相关菜单和操作。

## 10. 实施步骤

1. **规则确认**：确认钱包币种/精度配置、码是否允许绑定用户、订阅码生效策略、退款/提现边界。
2. **数据与服务层**：新增钱包账户/流水、兑换码批次/码/兑换记录；定义通用订单履约服务，接入并发锁与幂等约束。
3. **用户 API**：钱包查询/流水、兑换、兑换历史；扩展 `/billing/me`。
4. **钱包支付**：扩展订单创建分支，完成事务内扣款、已支付状态和商品履约。
5. **管理 API 与 Console**：批次创建、一次性导出、作废、钱包查询调账和权限。
6. **用户界面**：钱包余额展示、购买支付方式、兑换入口、流水和兑换记录。
7. **验证与发布**：覆盖并发兑换、余额不足、支付重试、商品变更后兑换、事务失败回滚、权限和审计；先通过内部小批量码灰度。

## 11. 验收标准

- 同一兑换码并发提交时至多一个请求成功履约；重试不会重复增加钱包/Token 或开通多个订阅。
- 兑换码创建后只可在创建响应中取得明文；管理端后续查询不泄露码值。
- 已失效、已作废、已兑换及未到生效时间的码均不能兑换。
- 余额码入账按创建时的钱包单位配置写入统一钱包账户与钱包流水，金额始终使用整数单位。
- 商品币种/精度与钱包单位不兼容或余额不足时，订单不标记已支付，钱包不扣款，商品不履约。
- 并发钱包支付不能透支；重复订单请求不会重复扣款。
- 钱包扣款、订单已支付、订阅/Token 履约和流水在同一事务内一致提交或回滚。
- 管理员调账必须记录原因和操作者，且不能删除或覆盖历史钱包流水。
- 用户无法通过修改请求参数读取/修改其他用户的钱包或兑换记录。

## 12. 待评审事项

以下为本方案的推荐默认值，请评审确认或调整：

1. **钱包单位**：是否接受全站统一配置钱包币种、最小单位精度和显示名称，账户只存整数余额；已有余额后变更单位必须执行迁移？
2. **码归属**：是否接受第一阶段使用不绑定用户的一次性兑换码？如需定向发码，应在批次/单码上增加目标用户限制。
3. **订阅生效**：订阅码是否完全复用当前订阅的续期/排队策略，还是希望兑换时立即切换？
4. **管理发码**：是否接受创建时一次性下载 CSV/文本文件，后续无法找回明文码？
5. **退款与提现**：是否接受第一阶段不支持用户提现和自助退款，只保留受审计的管理员调账能力？
